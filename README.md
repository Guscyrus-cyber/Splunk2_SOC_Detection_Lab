Attacker IP Identified

I ran index=main source="/var/log/auth.log" "Failed password" | rex "from (?<src_ip>[0-9a-fA-F:]+)" | stats count by src_ip | sort - count and the result returned ::1, which means the failed SSH login attempts came from the IPv6 localhost address; in this query, index=main tells Splunk to search the main index source="/var/log/auth.log" limits the search to the Kali Linux authentication log, and "Failed password" filters only the failed SSH authentication events, while rex "from (?<src_ip>[0-9a-fA-F:]+)" extracts the source IP address from the raw log line into a new field called src_ip,stats count by src_ip counts how many failed login events came from each extracted source IP, and sort - count places the highest count first; because the output showed only ::1, this confirms that all of the failed password attempts in this attack came from the same source, namely the local machine itself using IPv6 localhost rather than IPv4 "127.0.0.1",  which is normal because ssh fakeuser@localhost on Kali often prefers IPv6, and from a SOC perspective this step is important because it identifies the attacking source, proves that the multiple failed login events are linked to a single origin, and supports the conclusion that the activity was a concentrated brute-force attempt from one host rather than scattered failures from different systems.

Brute-force Detection

I ran index=main source="/var/log/auth.log" "Failed password" | rex "from (?<src_ip>[0-9a-fA-F:]+)" | bin _time span=5m | stats count by _time src_ip | where count >= 3 and received the result showing ::1, which confirms that three failed SSH authentication attempts were grouped within the same 5-minute time window from a single source IP address (::1), indicating a concentrated pattern of repeated login failures; because all attempts originated from the same IP, targeted the same invalid user (fakeuser), and occurred within a short time span, this behavior matches the definition of a brute-force attack, meaning that the query successfully detected brute-force activity rather than just listing failed events, and demonstrates that the detection logic is functioning correctly by correlating multiple failed login attempts into a single identifiable attack pattern.

Create Brute Force Threshold Detection Report


In this step, I created a more advanced detection rule based on time and frequency. I returned to the search interface and pasted a query that uses bin _time span=1m to group events into one-minute intervals. I then counted failed attempts per IP and filtered results where the count was greater than or equal to 3 , representing brute force behavior. After clicking Search , I verified that results showed timestamps and repeated attempts from ::1. I then clicked Save As  Report, named it Brute Force Detection (Threshold), wrote a description explaining the threshold logic, selected Statistics Table, and saved the report without scheduling it.

Query used:

index=main source="/var/log/auth.log" ("Failed password" OR "Invalid user")
| rex "from (?<src_ip>[0-9a-fA-F:]+)"
| bin _time span=1m
| stats count AS failed_attempts by _time src_ip
| where failed_attempts >= 3
| sort - failed_attempts
